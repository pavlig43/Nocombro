# Задание следующему агенту: выбрать следующий экран для UI

## Цель

Найти следующий экран, где UI-правка даст заметную пользу. Не назначать «Прибыльность» заранее и не переделывать уже готовые зоны.

## Старт

- Работать от актуального `master` в новой ветке.
- Сначала прочитать `docs/ui/next-ui-pass/implemented/README.md`.
- Не подключать подагентов без явного разрешения пользователя.
- Не предлагать single-формы, неизменяемые списки и «Оповещения» — они уже обновлены.

## Кандидаты

Проверить оставшиеся типы экранов:

- «Аналитика»;
- «Прибыльность»;
- «Пример таблицы»;
- «Склад»;
- «Эксперименты»;
- «Доктор».

Если нужен свежий снимок, попросить пользователя прислать его. Не тратить время на управление окном, если оно работает ненадёжно.

## Как выбрать

Оценить каждый экран:

- 0–4 — обрезанный текст, переполнение, плохая прокрутка и иные помехи работе;
- 0–3 — слабая иерархия и лишний цвет;
- 0–2 — разрыв с уже принятым видом;
- 0–2 — можно ли перенести решение на другие экраны этого типа;
- минус 0–2 — риск затронуть сложную логику.

При равенстве выбрать худший экран при 1280 × 800, затем экран с более общим каркасом. Пустое место само по себе не считать дефектом.

## Первый ответ пользователю

- Показать не больше двух кандидатов.
- Для каждого дать один свежий PNG и три коротких довода.
- Сразу назвать рекомендацию.
- Не рисовать макет и не менять Kotlin до ответа пользователя.
- Закончить вопросом: «Берём первый экран или второй?»

## После выбора

- Сделать PNG-макет 1280 × 800; HTML не делать.
- Брать цвета из темы, не вводить новую библиотеку и не задавать жёсткую ширину без причины.
- Проверить длинные русские подписи, числа, пустые состояния и прокрутку.
- Не менять функции экрана, состав данных, публичный API, БД и навигацию.
- Код менять лишь после явного одобрения макета.
- Запуск приложения, сборки и тестов согласовать с пользователем.
