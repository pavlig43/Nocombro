# YDB Mirror Sync

## Архитектура

Синхронизация работает только через typed mirror tables в YDB.

- Каждая business table имеет отдельную remote-таблицу.
- Ключ строки: `sync_id`.
- Межтабличные ссылки хранятся через `*_sync_id`.
- Победитель определяется по `updated_at` / `deleted_at`.
- Версии `updated_at` и `deleted_at` записываются в UTC и монотонно растут даже
  при откате системных часов.
- В схеме они остаются строками `LocalDateTime` без часового пояса. Код трактует
  только эти версии синхронизации как UTC. Пользовательские даты и время сохраняют
  прежнюю локальную семантику.
- Удаления распространяются как tombstone через `deleted_at`.
- Бинарные файлы хранятся в S3, в YDB синхронизируются только metadata.

Legacy transport удалён:

- нет `sync_push_log`;
- нет cursor paging;
- нет legacy gateway или mock fallback;
- нет queue runner и JSON remote payload;
- `SyncService` выполняет только mirror reconciliation.
- локальная таблица `sync_change` удаляется миграцией Room 6 -> 7;
- legacy-колонка `sync_state.last_remote_cursor` удаляется той же миграцией;
- typed mirror rows применяются к Room напрямую, без legacy payload-моделей.

Инвентарь таблиц находится в
`database/src/desktopMain/kotlin/ru/pavlig43/database/data/sync/mirror/MirrorSyncTable.kt`.

DDL находится в `database/ydb/mirror_sync_v1.sql`. Приложение не создаёт
mirror tables во время работы. Таблицы нужно создать или мигрировать заранее
через SQL.

Для складов `MAIN`/`EXPERIMENTAL` перед выпуском клиента нужно применить
`database/ydb/migrate_storage_locations_v2.sql`. Пустое значение в поле
`storage_location` читается как `MAIN`. Старые клиенты нужно обновить до начала
создания транзакций `STORAGE_TRANSFER`.

Подробные правила складских операций и расчётов описаны в
[`docs/STORAGE_LOCATIONS.md`](docs/STORAGE_LOCATIONS.md).

Старые remote-таблицы приложение не удаляет. После выпуска новой версии,
успешного push/pull и проверки восстановления их можно удалить вручную SQL из
`database/ydb/drop_legacy_sync_tables.sql`.

## Локальные удаления

Физические удаления и SQLite cascade проходят через
`mirror_deletion_journal`.

Перед удалением сохраняются typed mirror rows, затем локальный snapshot
возвращает их как tombstone. Это позволяет отправлять удаления в порядке
child -> parent, не меняя существующее UI-поведение.

## Настройки

- `NOCOMBRO_YDB_JDBC_URL` или `nocombro.ydb.jdbcUrl`
- `NOCOMBRO_YDB_SA_FILE` или `nocombro.ydb.saFile`
- `NOCOMBRO_YDB_TOKEN` или `nocombro.ydb.token`
- `NOCOMBRO_YDB_MIRROR_ROOT` или `nocombro.ydb.mirrorRoot`

Если `jdbcUrl` не задан, используется default database URL.

На Windows service-account key по умолчанию также ищется в:

```text
%APPDATA%\Nocombro\ydb-sa-key.json
```

## Runtime

- При запуске UI сначала читает локальный `sync_state`. Удалённый статус
  проверяется только при запуске и не чаще раза в час. Время попытки хранится в
  DataStore и записывается до запроса. Периодического опроса YDB нет.
  Android хранит время попытки и последний показанный статус в своём DataStore
  и применяет тот же часовой лимит.
- Ручные команды проверки, push, pull и полной синхронизации обходят часовой
  лимит. Одновременно выполняется только одна команда.
- Проверка статуса использует по одному снимку Room и YDB. Этот же план формирует
  счётчики, конфликты и отчёт. Push, pull и полная синхронизация не запускают
  дополнительную проверку статуса после завершения.
  Android-проверка читает четыре мобильные mirror-таблицы по одному разу.
  Мобильные pull и полный цикл не запускают проверку статуса после работы.
- Проверка из одного `MirrorReconciliationPreview` готовит технический Markdown и
  HTML для бухгалтера в `%APPDATA%\Nocombro\sync-reports`: `latest-sync-analysis.md`
  и `latest-sync-analysis.html`. Оба временных файла записываются до замены целевых;
  каждый целевой файл заменяется атомарно. При частичном сбое показывается ошибка,
  а доступность и время каждого отчёта читаются из его файла. Старый HTML не получает
  дату нового Markdown. Временные файлы удаляются, отчёты с датой в имени сохраняются.
- В меню синхронизации кнопка `MD` открывает Markdown прежним способом, кнопка `HTML`
  открывает сохранённый HTML в браузере по локальному URI. Кнопки зависят от наличия
  своих файлов и отключены на время операции. Открытие не создаёт отчёт и не читает
  Room, YDB или S3. Старый Markdown без HTML оставляет кнопку `HTML` недоступной.
- Кнопки отчётов подписаны `MD` и `HTML`, используют один стиль текста без иконок.
  Нули до успешной проверки не означают, что базы совпадают: интерфейс пишет
  «не проверено». Дата сохранённого отчёта показана отдельно и не подменяет дату
  успешной проверки в текущем запуске. Ошибка имеет приоритет над надписью о совпадении баз.
- HTML строится из типизированных строк обоих снимков: связанные записи собраны в
  блоки операций, товаров, поставщиков, документов и опытов. Денежные движения
  показываются отдельно. Добавления и восстановления зелёные, удаления красные,
  у правок и конфликтов жёлтые только различающиеся поля. Контекст неизменённого
  родителя не помечается как правка. Счётчики считают исходные действия плана;
  строки с недоступными зависимостями вынесены в «Не включено в план» и не меняют план.
  Неизменённый родитель показан кратко: название, для партии — товар и дата.
  Строки без различий в деловых полях скрыты, число служебных обновлений приведено
  отдельно. Они остаются в плане и техническом Markdown. Ссылки на изменения партий
  вынесены под таблицу, поэтому наличие ссылки не меняет колонки товарных строк.
  В переносе между складами две новые активные записи одной партии с равным
  количеством показываются одной строкой «Перенос»: только склады «Было / Стало»
  выделены жёлтым. Оба исходных движения остаются в плане и его счётчиках.
  Неполные, спорные и неоднозначные пары показываются отдельными записями.
  Блоки операций, документов, отдельных расходов и денежных движений идут по дате
  самого документа, от ранних к поздним. Связанные строки остаются в одном блоке.
  Товары, партии и справочники без даты документа идут после него, по названию;
  партии внутри товара — по дате партии. Служебные версии не задают порядок отчёта.
- Полные небольшие выборки JDBC используют `useStreamResultSets=false`. После
  `CLIENT_RESOURCE_EXHAUSTED` соединение закрывается. Чтение повторяется с паузами
  2 и 5 секунд. Условная запись повторяется с паузами 2, 5 и 10 секунд: batch-DML
  идемпотентен по `sync_id` и версии, поэтому неоднозначный ответ после принятой
  записи не создаёт дубль и не затирает более новую строку.
- Push группирует локальных победителей по mirror-таблице. Все строки одной таблицы
  передаются параметром `List<Struct<...>>` и записываются одним условным DML, после
  которого тот же запрос возвращает фактических победителей. Число запросов зависит
  от числа затронутых таблиц, а не от числа строк.
- Push сравнивает local и remote snapshots, применяет remote winners локально и
  отправляет local winners в mirror tables. YDB принимает строку только тогда,
  когда её версия не старше входящей; принятые и отклонённые строки возвращаются
  отдельно.
- На desktop новый файл сначала копируется в каталог Nocombro и сохраняется в
  Room с заранее созданными `sync_id` и `remote_object_key`. Сеть для сохранения
  формы не нужна.
- Перед записью локальных file-победителей в YDB sync загружает их бинарные копии
  в S3. При ошибке одного файла весь пакет YDB и последующий pull не запускаются.
  Следующий ручной sync повторяет S3 → YDB по той же более новой строке Room.
- Tombstone и старые строки `file` без `remote_object_key` в S3 не отправляются.
  Push без файлов не требует настроенного S3.
- После отклонённого push клиент один раз заново загружает remote snapshot и
  повторяет reconciliation. Если локальная версия всё ещё новее, выполняется одна
  повторная условная запись. Второе отклонение завершает операцию ошибкой.
- Pull применяет remote winners локально.
- Равные версии с разными данными считаются конфликтом. Doctor позволяет выбрать
  локальную или удалённую строку и создаёт новую версию выбранного варианта.
- После pull отсутствующие бинарные файлы догружаются из S3.
- Doctor при запуске и смене инструмента не читает YDB. Удалённая сверка
  Room, mirror `file`, реестра загрузок и S3 запускается только кнопкой
  «Обновить».
- Снятие блокировки удаляет только локальную запись о загрузке. Объект остаётся в
  S3 до отдельной сверки и удаления.
- Перед каждым удалением Doctor заново читает Room, YDB, реестр загрузок и S3.
  Ошибка любого источника блокирует удаление. Новые записи в старый реестр
  незавершённых загрузок больше не создаются.
- Восстановление пустой Room-БД выполняется обычной кнопкой синхронизации.

## Удаление legacy tables

1. Установить новую версию на все рабочие машины.
2. Проверить, что status показывает доступный mirror без ошибки.
3. Выполнить push/pull и убедиться, что local и mirror совпадают в Doctor.
4. Проверить восстановление тестовой пустой Room-БД.
5. Сделать резервную копию или экспорт старых YDB-таблиц.
6. Выполнить `database/ydb/drop_legacy_sync_tables.sql` вручную в YDB Query.

Приложение этот SQL не запускает.

## Проверки

Отчёт на реальных данных без интерфейса Nocombro:

```powershell
.\tools\show-sync-report.ps1
```

Скрипт получает согласованную временную копию SQLite через `sqlite3.backup`, включая
WAL, затем запускает `:database:syncAnalysisReport`. Служебный запуск читает одну
пару снимков, строит план тем же `MirrorReconciliationPlanner` и сохраняет оба отчёта
тем же `SyncAnalysisReportWriter`. Он не применяет план, не пишет в исходную SQLite
или YDB и не обращается к S3. Временная копия удаляется в `finally`, отчёты остаются.
Параметр `-NoOpen` сохраняет отчёты без открытия браузера. `-DatabasePath` и
`-ReportDirectory` задают источник и каталог отчётов.

Целевая проверка отчётов и статуса:

```powershell
.\gradlew.bat :database:desktopTest --tests '*SyncAnalysis*Test' --tests '*SyncServiceMirrorStatusTest' --tests '*MirrorReconciliationPlannerTest'
.\gradlew.bat :rootnocombro:desktopTest
```

Обычные локальные тесты:

```powershell
.\gradlew :database:desktopTest
.\gradlew :rootnocombro:desktopTest
```

Реальный YDB smoke test:

```powershell
$env:NOCOMBRO_YDB_SMOKE = "true"
.\gradlew :database:desktopTest --tests "ru.pavlig43.database.YdbMirrorIntegrationTest" --no-parallel
```

Disaster recovery test:

```powershell
$env:NOCOMBRO_YDB_DISASTER_RECOVERY = "true"
.\gradlew :database:desktopTest --tests "ru.pavlig43.database.YdbMirrorDisasterRecoveryTest" --no-parallel
```
